# 统一执行 DAG 与 Subagent 上下文编排

## 目标

为 Suncode 建立一套平台无关的执行计划模型：所有进入正式实施的任务都可以归一化为有向无环图（DAG），由 inline、平台原生 subagent 或 channel worker 按各自能力消费；每个可派发节点都携带最小、角色化、可审计、可回退的上下文包，使并行执行既能提速，也不会依赖复制主代理的完整会话历史。

## 背景与已确认事实

- 当前工作流以 `prd.md`、`design.md`、`implement.md` 和 implement/check JSONL 表达需求与上下文，但没有统一、机器可执行的依赖图。
- 当前 Codex 默认使用 inline；支持 subagent 或 channel 的平台可以派发 worker，但工作流仍主要按 implement → check 串行描述，没有系统地寻找全部就绪节点并并发执行。
- `task.json.subtasks` 是历史任务内检查项，`task.json.children` 是生命周期父子关系；二者都不是执行依赖图。
- Hub 的 `subtasks.json` v1 和上传哈希契约只包含 `priority`、`name`、`description`。不能在不破坏兼容性的前提下直接把它变成运行时 DAG 状态。
- channel worker 当前共享工作目录，没有内置 worktree 隔离。并行写入必须依赖明确且互斥的写范围；并行检查默认只能产生报告，由单一修复者整合。
- 现有上下文注入机制支持 hook 推送和 agent 主动拉取，但上下文仍以任务/角色为主，尚未针对 DAG 节点表达边界、依赖产物、预算、截断与来源证明。

## 用户价值

1. 开启 subagent 后，调度器能够真正利用互不依赖的工作并行提速，而不是主代理拆完任务后继续单线等待。
2. inline 和 subagent 使用同一份规划语义，避免同一个任务因执行平台不同而产生两套计划。
3. 子代理只接收完成当前节点所需的信息，降低上下文污染、错误继承和 token 浪费。
4. 执行过程可以回答“为什么这个节点现在能运行”“它读了哪些上下文”“它改动了什么”“失败后如何恢复”。
5. 旧任务、旧 Hub 上传和不支持 subagent 的平台仍可继续工作。

## 范围

### 1. 统一执行图

- 新增版本化的 `execution.json`，作为任务目录内唯一规范的执行 DAG 计划文件。
- DAG 节点至少表达：稳定 ID、名称、角色、描述、依赖、读写范围、验证要求、上下文配置、执行策略和优先级。
- 任务不论复杂度都可以归一化为 DAG；轻量任务可以是一节点 DAG。
- 图必须在实施开始前完成结构校验，包括 ID 唯一性、依赖存在性、无环性、角色合法性以及必要字段完整性。
- 计划文件保持稳定、可审查；运行中状态不得回写污染计划。

### 2. 规划器契约

- 规划阶段必须把可独立交付、可验证的工作拆成节点，并明确真实依赖，不能仅按文档顺序串成链。
- 节点粒度应允许独立验证和清晰回传，但不能细到调度成本超过收益。
- 规划器必须声明可能发生写冲突的资源；无法证明写范围互斥的节点不得并行写入同一工作区。
- 实施清单继续作为人类可读视图和旧工具回退入口，但不再承担规范 DAG 的职责。

### 3. 能力感知调度

- 调度器根据执行器能力选择 inline、原生 subagent 或 channel worker，而不是改变 DAG 本身。
- inline 执行器消费同一图，默认并发度为 1；无 subagent 平台可以安全地按拓扑序串行执行。
- subagent/channel 执行器每轮计算全部 ready 节点，在并发上限、资源冲突和角色约束下尽可能 fan-out。
- 调度器使用 wait-any 语义：任一节点完成后立即更新依赖并释放新的 ready 节点，无需等待整批完成。
- 图末尾必须有集成屏障和全局检查；局部节点通过不等于任务完成。

### 4. 并行安全

- 节点必须区分只读范围与写入范围，并允许声明逻辑资源锁。
- 共享工作区中，只有写范围被证明互斥的实现节点可以并行。
- 并行 reviewer/checker 默认只回传报告，不能直接修改共享工作树；修复由单一 fixer 节点完成。
- 将独立 worktree/容器作为可选执行器能力，不作为首版完成条件；未提供隔离时必须自动降级到安全调度。

### 5. 节点级 Subagent 上下文包

每个派发节点必须构造确定性的上下文包，至少包含：

- 任务身份：任务路径、任务 ID、DAG 版本、节点 ID、尝试次数、父会话/调度运行 ID。
- 角色与目标：角色、节点描述、完成定义、禁止事项、写入边界和验证命令。
- 需求依据：PRD，以及节点明确引用的 design、implement、spec、research 或源文件片段。
- 依赖信息：直接依赖节点的结构化结果、产物引用和必要摘要；不默认注入其完整 transcript。
- 执行约束：允许使用的执行器、超时、重试策略、资源锁、并发/隔离要求。
- 来源清单：每个上下文项的来源、类型、顺序、内容哈希、是否缺失、是否被截断以及截断原因。

上下文构建还必须满足：

- 顺序确定：相同计划、相同仓库状态和相同依赖结果应生成等价上下文。
- 最小披露：默认只注入节点需要的内容；任务级全量资料必须显式请求。
- 双层预算：支持单项预算与总预算；超限时按确定优先级裁剪，并显式记录截断。
- 敏感信息保护：不得把 secret、token、凭据或未授权环境变量写入上下文产物和日志。
- 推拉一致：平台 hook 自动注入失败或不可用时，agent 可按同一 manifest 主动拉取，内容语义保持一致。
- 会话隔离：支持干净上下文的平台必须使用隔离派生；Codex 原生 subagent 使用 `fork_turns = "none"`，不复制主会话历史。
- 结构化回传：子代理返回节点状态、摘要、变更/报告、验证、产物引用、风险和后续建议，主代理不依赖完整 transcript 才能继续调度。

### 6. 运行时状态与可观测性

- DAG 计划保存在任务目录；运行状态保存在 `.suncode/.runtime/`，二者职责分离。
- 运行状态至少记录节点状态、分配执行器、尝试次数、时间戳、失败分类、依赖结果引用和上下文 manifest 哈希。
- 状态更新应可恢复且尽量原子化；进程中断后可重新计算 ready 集合，不重复提交已确认成功的节点。
- 日志必须能追踪：调度决策、降级原因、上下文包来源、实际派发目标和节点结果，但不打印敏感正文。

### 7. 兼容与迁移

- 不修改历史 migration manifest；通过新的迁移版本分发模板、hook、平台文件和文档变更。
- 旧任务没有 `execution.json` 时仍可执行：
  - 简单任务归一化为隐式单节点；
  - 只有 `implement.md` 清单时按原顺序生成保守串行链；
  - 只有 `subtasks.json` v1 时可生成展示节点，但不得推断并行安全。
- 当 `require_for_complex_tasks` 启用时，新建复杂任务必须生成显式 `execution.json`；迁移不批量改写用户现有任务。
- 功能需提供配置开关和安全回退：功能关闭或旧任务没有图时继续使用现有串行工作流；显式 `execution.json` 损坏时必须阻止实施并给出明确诊断，不能静默忽略用户计划。

### 8. Hub 投影

- `subtasks.json` 保持 Hub v1 展示/覆盖文件，规范字段仍为 `priority`、`name`、`description`。
- Hub 上传优先级为：显式 `subtasks.json` v1 → 从 `execution.json` 节点投影 → 从 `implement.md` 清单回退。
- 从 DAG 投影到 Hub 时只发送 v1 三字段，不把依赖、资源、上下文或运行状态混入请求与哈希。
- DAG 上传/跨设备协作若未来需要完整图，必须另行定义版本化 Hub API，不在本任务中暗改现有 API。

### 9. 跨平台一致性

- 共享核心负责图解析、校验、归一化、上下文 manifest 和调度状态机；平台适配层只负责能力声明、派发、等待、取消和结果转换。
- Claude、Codex、Cursor、CodeBuddy、Droid、Kiro、OpenCode、Gemini、Qoder、Reasonix、ZCode、Pi、OMP、Trae、Grok、Kimi 等已支持表面必须有明确的适配或安全回退行为。
- 平台原生 hook、agent 模板、channel 工作流和文档必须从同一上下文协议派生，不能各自发明字段语义。

## 非目标

- 首版不建设跨机器分布式调度器。
- 首版不自动理解任意代码语义并无人工约束地推断可并行写范围。
- 首版不自动合并两个同时修改同一文件或同一符号的 worker 结果。
- 首版不要求 channel 自动创建 worktree、容器或远程沙箱。
- 首版不变更 Hub v1 API、哈希格式或既有任务父子生命周期语义。
- 首版不以记录或回放完整 subagent transcript 作为恢复机制。

## 验收标准

- [x] 新任务可生成并通过校验的 `execution.json`；单节点与多节点 DAG 均有覆盖。
- [x] 校验器能拒绝重复 ID、缺失依赖、自依赖、环、非法角色和不完整的写入/验证约束，并输出可定位的错误。
- [x] inline 模式使用同一 DAG 且按拓扑顺序完成，默认并发度为 1。
- [x] 能力允许时，两个无依赖且写范围互斥的 ready 节点会在主代理等待前全部派发。
- [x] 任一节点完成后能立即释放其后继；不要求同批其他节点先完成。
- [x] 写范围冲突或缺少隔离能力时，调度器会串行化或拒绝危险并行，并记录原因。
- [x] 并行 check/review 节点在共享工作区默认只读；修复经单一 fixer 节点完成。
- [x] 每次 subagent 派发都有确定性的上下文 manifest，包含来源、顺序、哈希、预算和截断信息。
- [x] 节点上下文只包含显式需求与直接依赖结果；不会默认携带主代理完整历史或无关节点 transcript。
- [x] Codex 原生 subagent 派发使用 `fork_turns = "none"`，并验证父会话/任务隔离。
- [x] hook 推送与 agent 拉取回退生成语义一致的节点上下文；缺失、seed-only、目录扩展、损坏 JSONL 和预算超限均有测试。
- [x] subagent 的结构化结果足以驱动后续节点和最终集成，不需要解析自然语言 transcript。
- [x] 中断后可以从 `.suncode/.runtime/` 恢复未完成图，已成功节点不会无条件重复执行。
- [x] 没有 `execution.json` 的旧任务继续按安全串行路径运行。
- [x] 显式 `subtasks.json` v1 的 Hub 上传内容和哈希保持不变；无覆盖文件时可从 DAG 正确投影三字段。
- [x] 新 migration manifest、模板复制、初始化/更新/卸载、registry invariants、Hub、workflow 和核心 DAG 测试全部通过。
- [x] 英文与中文文档说明统一 DAG、执行器能力、上下文包、并行安全、回退和迁移行为。

## 成功指标

- 对具备至少两个独立节点的基准任务，subagent 模式能观察到真实重叠执行，而 inline 结果保持等价。
- 节点上下文大小可量化且默认小于任务全量上下文；所有裁剪均可审计。
- 兼容测试证明旧任务与 Hub v1 请求没有行为回归。
- 出错时用户能从一次诊断输出定位图校验、资源冲突、上下文构建、派发或节点执行中的具体阶段。

## 开放问题

无阻塞产品问题。worktree 隔离、完整 DAG 的 Hub 同步和自适应并发策略作为后续独立能力评估。
